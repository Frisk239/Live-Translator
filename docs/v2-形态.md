# 第二形态

形态已实现（分支 `feat/hosted-listen-captions`，测试全绿、待部署验证）。真相源是 [hosted-listen-spec.md](./hosted-listen-spec.md)。

同一个产品：观众仍在自己电脑上看英 / 日 / 韩直播，字幕窗长得和第一形态一样。差别只有一处——开听之后，听译可以在我们这边做。

词见 [CONTEXT.md](../CONTEXT.md)。决定见 ADR 0005、0009–0033。第一形态见 [v1-形态.md](./v1-形态.md)。

## 为什么是这个形态

托管听译的头部做法（Deepgram / Soniox / OpenAI Realtime）都是：客户端推声音，服务端回草稿和定稿。只传字的话，本机还得跑识别，拆不开，也撑不起「我们出算力」。

通用 LLM 不当默认翻译。讯飞、豆包同传赢在专用同传模型和术语，不是 GPT 套壳。微信 / 飞书那种「格外准」多半是说完一整段再改，抄到直播字幕上会空一截、变成语音条。

## 观众怎么用

1. 仍从托盘打开控制面板，选音源。
2. 要开托管听译，先登录账号。
3. 按开始：字幕窗出现，本机把该音源的声音送到我们这边，字幕按第一形态的规则上屏（一条、流式草稿、切条定稿、静默两秒撤条）。
4. 停止：停传声音，字幕窗撤掉。被顶或真断网：停听并告诉观众，不要默默改回本机听译。短闪断或计划内上线：壳再开听。

音源、字幕模式、窗的位置仍记在本机。账号和在听会话在我们这边。第一版不限额。

## 两边各干什么

- **观众电脑**：音源、字幕窗、控制面板、账号登录。不跑听译，不向观众要任何 API key。
- **我们**：听、译、切条，把草稿和定稿送回。开源识别 + 开源译中文。不存录音；开听结束，声音丢掉。

切条仍跟嘴走，规则与第一形态相同，放在我们这边做（认字的人决定何时切）。

## 和第一形态的关系

不是两个软件。观众看见的壳是一份；听译有本机、托管两处。第一形态已接通本机听译。第二形态补上托管服务，控制面板默认露出本机|托管分段。三个并列目录会把字幕窗复制两遍，仍不建。

## 第二形态不做

- 不让观众填 LLM / 翻译的 key
- 不用 LLM 做默认翻译，也不做定稿润色
- 不配音
- 不把声音留下来训练或回放
- 不在托管失败时悄悄掉回本机听译
- 仍不给主播叠字、不拆同一浏览器两个标签、不让观众调切条快慢
