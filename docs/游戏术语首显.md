# 译文质量：靠 LLM 纠正，不靠词表

词表/黑名单已否决。boss fight → 老大争斗只是 CT2 硬译的一个例子，要修的是**整句译不准**，不是某一批游戏词。

路线总图：`docs/听译优化路线.md`。

---

## 1. 别人怎么做（源码 + 公开管线）

近邻和公开 demo **都没有**「NMT 先出再黑名单替换」。译文就是 LLM（或 Google/DeepL）自己译的。

| 谁 | 译者 | 观众先看到什么 |
| --- | --- | --- |
| SakiRinn/LiveCaptions-Translator | LLM 或 Google/DeepL，队列异步 | 原文立刻有；译文等 API 回来再上屏。完成句会 choke 720ms 让人看清。新请求取消更早的未完成请求。 |
| TheDeathDragon/LiveTranslate | 只用 LLM，流式 `translate_iter` | ASR 原文先出；译文从第一个 token 往外长。电竞预设是「游戏术语留原文」，那是 prompt，不是词表。 |
| LiveKit live-translated-captioning | STT → 整句喂 LLM | 没有 Marian 保底。 |
| KazKozDev/live-translation | Whisper → 本地 LLM | **整句**才送去译，避免逐词 MT。 |
| NVIDIA NeMo 流式语音翻译 | ASR 流 → LLM 译 | wait-k / 最长公共前缀，控制「读多少再写」；也不是 NMT+词表。 |

学术上字幕允许修订（re-translation）：同一句可以改。我们的产品是「下一条立刻挤掉上一条」，改写必须落在**这条还在屏上的时候**。

---

## 2. 我们为什么 LLM 没纠正上

不是模型不会译。同句 A/B：flash 给「首领战 / 3000点生命值」，CT2 给「老大争斗 / 3000赫普」。

真窗日志（普适，不限于游戏）：

1. **预取打在第一条草稿上**（`So we.`），一条只发一次。整句还没说完，请求已经浪费。
2. **定稿改写刚 start，下一条 ~1s 切条**，`bar_seq` 变了就 abort。TTFT 约 0.8–1.2s，和条的寿命撞车。
3. 所以观众整条寿命里看到的都是 CT2。

回放 6/6 覆盖是因为回放切条慢。真窗语速下改写赢不了切条——**所有硬译**都这样，不单 boss。

---

## 3. 普适做法（配了 LLM 时）

原则不变：没配 LLM = 纯 CT2；HTTP 不进重活线程；草稿仍可 CT2 保开口。

要让 LLM 成为真正的译者，改**何时发、何时作废**，不改词表：

1. **预取等草稿够长再发**（仍每条一次，不增加 req/s）。打在接近整句的草稿上，定稿出生才用得上。
2. **定稿改写不被下一条的预取掐死**（双槽已有；新条作废旧条是对的，因为无处上屏）。质量靠第 1 条在切条前就跑完。
3. 仍做不到的短条：接受这条寿命内是 CT2，下一条不回溯。不要为译准去同步等 LLM 再切条（已证伪，会堵识别）。

不靠：加长提示词、翻倍预取、用户术语表、CT2 出口黑名单。
