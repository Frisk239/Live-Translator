# 定稿改写调度

真窗里改写常落不了地：条的寿命 ≈ LLM 首字，下一条立刻挤掉并 abort。模型会译对，请求没贴上屏。

---

## 目标

配了 LLM 的「本机 + 改写」：多数定稿条能看到改写后的译文。识别不堵。没配 LLM 行为不变。req/s 仍 ≤1。

## 两刀一起做

### 1. 请求：够长再预取

预取仍每条一次。改写路径也走 `draft_worth_llm`（≥4 个英文词或 ≥8 字），不要打在 `So we.` 上。

本机 LLM 直译已经这样。本机改写对齐。

### 2. 上屏：定稿最短亮 1s，改写没到最多 2s

定稿后 `_hold_from = now`：

- 前 1s 必亮，`bar_seq` 不变
- 若改写还在飞，再等到落地或 2s 上限，避免 1s 一到 bump 把请求掐死
- 这 1–2s 内下一条不上屏；识别继续
- **hold 期间预取下一条**（lookahead，不占当前条的 seq，不 abort 当前改写）。切过去时出生就能用 LLM
- 停听先 `wait_llm` 最多 3s，最后一条改写能发出去再清会话

对照：SakiRinn choke 720ms；Wakaru 最短 2.5s 且新条排队。

## 不改

切条规则（口气/句末/硬顶）、草稿 CT2、词表、翻倍预取、同步等 LLM 再 `take()`。

## 验收

- pytest：短草稿不预取；hold 期内下一条草稿不上屏；hold 期内改写能写上当前定稿。
- 回放 `en_speech.wav` 改写模式：同一原文先 CT2 再出现更顺译文（boss/HP/regroup 类）。
